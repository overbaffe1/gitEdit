# Маяк из осколков

18 ноября 2026. После обратимого волнового поля — другая причина, по которой потеря части данных ещё не означает потерю результата: **избыточное кодирование**.

Своя маленькая пиксельная картинка маяка сохраняется в PNG, делится на шесть последовательных data-блоков и получает четыре parity-блока. Любые шесть из десяти возвращают **исходные байты файла**, а не приблизительно похожее изображение.

Это небольшой образовательный systematic Reed–Solomon erasure code на основе Vandermonde-матрицы. Не production storage, не шифрование, не Shamir secret sharing и не полноценный декодер неизвестных ошибок. Кодирование происходит после PNG-сжатия: decoder работает с произвольными байтами и вообще не обязан знать формат картинки.

## Свой маяк, а не скачанная картинка

[generate.py](samples/shards/generate.py) рисует сцену 96 × 64 стандартными примитивами Pillow: башня, световой сектор, островок, месяц, звёзды и море. Никаких внешних изображений, генеративной дорисовки, пользовательских данных или сетевых запросов. Исходный файл — [source.png](../assets/shards/source.png), **925 байт**.

Его SHA-256:

```text
ce7345053cba4da236baf51e8b4809791df0d78cb42b92b00647ec54a4b058d0
```

PNG доступен для независимого сравнения, **не является входом декодера**. После записи фрагментов генератор перечитывает опубликованные JSON и создаёт панели именно из них. Исходные байты остаются только для проверки совпадения.

## Алгебра без float

Работаем в `GF(2⁸)`, представляя элемент байтом. Сложение/вычитание — XOR, умножение — polynomial multiplication modulo:

```text
x⁸ + x⁴ + x³ + x² + 1    (0x11d)
```

Здесь `128 × 2 = 29`, а не 256 и не 0. Для любого ненулевого элемента `a⁻¹ = a²⁵⁴`. Таблица умножения в Python и JS строится локально простым shift/XOR, не загружается из файла.

Берём десять различных точек поля `x = 1,2,…,10` и Vandermonde-матрицу:

```text
V[i,j] = x_i^j,  j = 0,…,5
A = первые шесть строк V
G = V A⁻¹
```

Первые шесть строк `G` образуют identity. Поэтому первые шесть фрагментов — обычные последовательные data-блоки, последние четыре — parity, линейные комбинации всех шести. Для каждой позиции внутри блока:

```text
y = G d
```

Где `d` — шесть исходных байтов на этой позиции, `y` — десять кодированных. Это не разрез изображения на десять пространственных кусочков: плитки слева показывают значения **байтов блоков**, а не соответствующие участки маяка.

Если доступны шесть строк с индексами `S`:

```text
d = inverse(G[S]) y[S]
```

Любые шесть строк `V` обратимы: determinant квадратной Vandermonde — произведение попарных разностей её различных точек, все множители ненулевые. Умножение справа на `A⁻¹` сохраняет эту обратимость. Поэтому это не удача одного выбранного набора.

Инверсия — Gauss–Jordan **в конечном поле**, не `numpy.linalg.inv`, rounding или вещественное решение системы. Численные допуски не нужны: восстановление должно быть побайтово точным.

## Сколько стоит возможность потерять четыре блока

| Величина | Размер |
| --- | ---: |
| Исходный PNG | 925 байт |
| Размер data/parity блока | 155 байт |
| Шесть data-блоков после padding | 930 байт |
| Padding | 5 нулевых байт |
| Все десять кодированных тел | 1550 байт |
| Десять JSON-фрагментов с Base64 и метаданными | 4740 байт |

Идеальный множитель `10/6 ≈ 1,667`, здесь немного больше из-за padding. JSON/Base64, индексы и повторяемые хеши ещё увеличивают размер; ZIP сжимает обёртку отдельно. Это **не сжатие** и не «восстановление информации из ничего»: данные заранее получили избыточность.

Выживание любых четырёх потерь блоков не означает переживание любой аварии: если все фрагменты лежат на одном диске/в одном аккаунте/в одной папке, общая причина может уничтожить их все. Распределённое размещение и резервные копии остаются отдельными задачами.

## Формат фрагмента

Каждый из [десяти JSON](../assets/shards/fragments.md) содержит:

- `format = gitedit-shards-v1`, фиксированные `k = 6`, `n = 10`;
- `index` **0…9** (в подписях и именах файлов для человека **1…10**);
- исходный `size`, общий `sha256`;
- `block_sha256` тела именно этого фрагмента;
- `data` в Base64.

Метаданные самодостаточны: отдельный manifest декодеру не нужен. Проверяются формат, диапазон индекса, размер, одинаковая исходная длина/общий хеш, отсутствие дублирующихся индексов, длина тела и хеш каждого выбранного блока. Затем декодируются первые шесть выбранных корректных строк, padding отрезается по исходной длине и проверяется итоговый SHA-256.

Переданные дополнительные блоки тоже проходят проверки целостности, но не используются для исправления неизвестных ошибок. В CLI поддержан собственный формат с ограничением заявленного исходного размера 10 MB; это защитная проверка формата, **не обещание производительности** и не hardened parser для враждебных файлов.

## Что происходит на границе

### Шесть или больше

Доступны любые шесть **различных корректных** фрагментов одной группы — есть точное восстановление. Показательный набор: фрагменты **1,4,7,8,9,10**, то есть только два из шести исходных data-блоков и все четыре parity.

Проверены все `C(10,6) = 210` минимальных наборов. [recoveries.csv](../assets/shards/recoveries.csv) хранит индексы, SHA-256 и факт exact match для каждого. В живом приложении файл не подменяется на заранее нарисованный результат: решается матрица, формируются PNG-байты, проверяется хеш и лишь затем байты передаются браузерному PNG-декодеру.

### Пять

Пять строк дают не больше пяти независимых линейных уравнений на шесть неизвестных байтов в каждом stripe. Без дополнительных предположений произвольный файл не определён однозначно. Поэтому наш decoder **отказывает**, а не показывает приблизительное изображение или устаревший предыдущий результат.

Это не доказательство невозможности восстановить **конкретно этот маленький PNG** со всеми внешними знаниями: структура формата, словарь возможных картинок, опубликованный исходник и brute force — другие задачи. Хеш также задаёт дополнительные ограничения, но приложение не использует его как oracle для перебора. Утверждение «меньше шести ничего не раскрывают» было бы неверным: систематические data-блоки содержат настоящие последовательные байты файла.

### Повреждённый байт

Кнопка переворачивает один бит первого байта первого выбранного блока, не меняя его ожидаемый хеш. Проверка блока отказывает. Его можно исключить вручную, а если целых останется хотя бы шесть — восстановить файл из них.

Ни Python, ни браузер не ищут автоматически неизвестный плохой блок и не применяют Berlekamp–Welch, syndrome decoding или поиск комбинаций. Даже если выбраны все десять, текущий интерфейс сначала сообщает о повреждении, а не прячет проблему. Сброс возвращает исходные фрагменты.

**Erasure и error — разные вещи.** Когда плохой блок уже известен, его можно отбросить и превратить error в erasure, но обнаружение и доверие к метаданным — отдельный слой.

### Почему SHA-256 не делает это защищённым хранилищем

Контрольные суммы лежат рядом с данными. Они полезны для этого воспроизводимого опыта и обнаружения случайной порчи относительно ожидаемых значений. Но тот, кто может заменить все блоки и все хеши, может представить другой самосогласованный файл. Цифровой подписи, доверенного manifest и аутентифицированного транспорта здесь нет.

Нет шифрования, пароля, случайных масок или secret sharing. Прежние визуальные «два листа» в галерее решают другую задачу — не следует переносить их модель секретности на эти фрагменты.

## Живой опыт

[bench.zip](../assets/shards/bench.zip) содержит один `bench.html`: десять кодированных блоков, их метаданные, собственные GF-операции и UI. **Полного исходного PNG, его Base64, внешних картинок, кадров GIF и сторонних библиотек в нём нет.** Наличие всех десяти фрагментов, конечно, алгебраически достаточно для восстановления; это не попытка скрыть изображение.

Открывается после распаковки через `file://` в проверенном Chromium, без сервера и сети. Использует стандартный `crypto.subtle.digest` для SHA-256; браузер должен разрешать Web Crypto в локальном контексте. Если API недоступен, опыт не заявляет успешное восстановление. Файлы загружать не требуется: кнопка порчи работает только с копией встроенных блоков в памяти.

Есть checkbox для каждого фрагмента, набор с четырьмя parity, пять блоков, все десять, порча, reset и скачивание восстановленного PNG. Управление доступно с клавиатуры; результат и причина отказа — текстом. Анимации внутри HTML нет. При каждом пересчёте старое изображение и download очищаются; асинхронная проверка защищена от показа устаревшего результата при быстрых переключениях.

В README работает GIF/reduced-motion постер и обычные ссылки. JS не исполняется в Markdown — локальный опыт запускается отдельно.

## Повторить без генератора и Pillow

Скачай [fragments.zip](../assets/shards/fragments.zip) и [codec.py](samples/shards/codec.py), распакуй фрагменты. Декодеру нужна только стандартная библиотека Python:

```sh
python3 codec.py \
  fragment-01.json fragment-04.json \
  fragment-07.json fragment-08.json fragment-09.json fragment-10.json \
  --output recovered.png
```

PNG, generator, source art, Pillow, NumPy и сеть для этой команды не нужны. В репозитории можно проверить так:

```sh
python3 atlas/samples/shards/codec.py \
  assets/shards/fragments/fragment-01.json \
  assets/shards/fragments/fragment-04.json \
  assets/shards/fragments/fragment-07.json \
  assets/shards/fragments/fragment-08.json \
  assets/shards/fragments/fragment-09.json \
  assets/shards/fragments/fragment-10.json --output /tmp/recovered.png
cmp assets/shards/source.png /tmp/recovered.png
```

Для перерисовки своего маяка, упаковок и GIF нужен Pillow:

```sh
python3 -m venv .venv
.venv/bin/pip install -r atlas/samples/shards/requirements.txt
.venv/bin/python atlas/samples/shards/generate.py --output /tmp/shards
```

Генератор не редактирует README и не делает сетевых запросов. JSON, CSV, ZIP и картинки воспроизводятся побайтово в закреплённом окружении; даты ZIP фиксированы. Формат свой, cross-library compatibility с просмотренными библиотеками не проверялась и не обещается.
