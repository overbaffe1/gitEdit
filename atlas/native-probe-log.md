# Нативные эксперименты: два кандидата, пока без нового стенда

18 ноября 2026. Ограничение пользователя: **всё должно работать внутри README**, без отдельного сайта и backend. В этом проходе рабочий новый приём не подтверждён. Корневой README, прежние экспонаты и workflows не менялись.

## 1. Поиск браузера как секретная команда

Идея: спрятать кодовое слово в закрытом `details`, затем поиском раскрывать нужную панель. Это было бы похоже на командную палитру без собственного поля ввода и JS.

Проверен HTML из **GitHub Markdown API с `context: overbaffe1/gitEdit`**, открытый локально в Chromium 153.0.8010.0:

- два закрытых `details` с одинаковым `name` сохранены;
- контрольный **видимый** текст присутствует в `body.innerText`, но `window.find()` возвращает для него `false`;
- `window.find()` на коде внутри **закрытого** блока тоже возвращает `false`;
- оба блока остаются закрытыми.

**Проверка поиска неинформативна:** положительный контроль не прошёл, поэтому отрицательный результат для скрытого текста нельзя приписать именно `details`. Скрипт явно выводит `INCONCLUSIVE`, а не объявляет поиск скрытого текста невозможным. `window.find()` — нестандартный API, а не гарантированный эквивалент настоящего интерфейса Ctrl+F. Browser chrome с Ctrl+F здесь не проверялся. Нельзя ни объявить готовой «консоль README», ни по этому отрицательному результату доказать, что Ctrl+F никогда не раскрывает `details` в обычном браузере.

Не путать с уже проверенным [fragment-квестом](fragment-quest.md): переход к id внутри закрытой секции и поиск текста — разные механизмы.

### Что было в исходниках WPT

В названиях двух найденных WPT-файлов есть `auto-expand`, `window-find` и `findstring`, но оба — **crash-регрессии**. В них нет утверждений, что поиск скрытого текста должен его найти и раскрыть. Само имя теста — не доказательство нужного пользовательского поведения. Эти файлы не запускались как тестовый harness WPT и не вставлялись в README.

## 2. Призрак перетаскиваемой картинки как прозрачная маска

Идея: использовать стандартное полупрозрачное drag-feedback изображение, чтобы совместить две картинки. Для пробы взяты уже существующие собственные PNG-доли из [демонстрации с корабликом](veil.md); новые картинки не создавались.

Что подтверждено:

- GitHub Markdown API сохраняет оба `img`, добавляет обычные ссылки-обёртки;
- обе картинки загрузились и декодировались в локальном Chromium;
- mouse down + движение от первой ко второй запускает **реальный `dragstart` на IMG**;
- среди типов drag data присутствуют `text/uri-list`, `text/html`, `Files`;
- Escape и отпускание мыши отменяют операцию без drop и навигации.

Что **не подтверждено**:

- что ghost-копия сохраняет нужные размер, масштаб, непрозрачность и точную регистрацию;
- что совмещение действительно показывает кораблик;
- что это удобно на github.com, в другом браузере или на телефоне.

Обычный снимок страницы во время drag показал исходные картинки, но **не сам drag-feedback overlay**. Поэтому он не является ни доказательством успешного визуального наложения, ни доказательством отсутствия ghost во всём браузере. Это другой слой UI. Событие `dragstart` тоже не доказывает, что задуманный оптический эффект виден.

**Итог:** эксперимент остаётся непроверенным кандидатом и в README не добавлен. Упоминание стандартного `setDragImage()` в документации объясняет фон, но вызывать его в README собственным обработчиком нельзя: это уже был бы наш JavaScript. В диагностическом скрипте кастомный drag image не задаётся.

## Что не делали

- Не добавляли нарисованные «рабочие» контролы или неработающие инструкции в главный README.
- Не запускали внешний сайт, backend, Actions, Codespaces или платные услуги.
- Не подменяли native drag своей DOM-картинкой, canvas или приложением.
- Не выдавали headless/browser API-тест за проверку production github.com и его интерфейса.
- Не делали drop файла/ссылки и не изменяли настройки аккаунта.

Это журнал отбора, а не новый экспонат и не утверждение, что нативные возможности исчерпаны.

## Источники

[Четыре файла с постоянными SHA и URL](samples/native_probes/sources.json):

1. MDN `Window.find()` — статус non-standard, параметры и результат поиска.
2. MDN `DataTransfer.setDragImage()` — описание автоматически создаваемого полупрозрачного feedback и отличия от кастомного изображения.
3. WPT `auto-expand-window-find-crash.html` — полностью прочитанная небольшая crash-регрессия, не функциональное доказательство поиска.
4. WPT `details-findstring-crash.html` — то же ограничение для другого найденного crash-теста.

Небольшие WPT-файлы прочитаны целиком, в документах MDN использованы соответствующие описания и предупреждение о нестандартности. Внешние баг-трекеры по ссылкам из этих файлов не объявлены прочитанными.

## Повторить диагностику

[Скрипт](samples/native_probes/check-browser.cjs) — **тестовая автоматизация**, не код, вставленный в README. Он получает ответ Markdown API, открывает его локально, выполняет контрольный поиск и нативный drag, затем печатает наблюдения. Отрицательный результат поиска не зашит как вечное правило: если браузер изменится, скрипт сообщит новое наблюдение.

Нужны Node 22+, настроенный `gh` и доступ к npm:

```sh
npm install --prefix .local/find-probe --no-audit --no-fund playwright-core@1.65.1 @sparticuz/chromium@153.0.0
node atlas/samples/native_probes/check-browser.cjs
```

На минимальном Linux без NSS/NSPR в этой сессии использованы библиотеки из того же локального npm-пакета:

```sh
NATIVE_PROBES_BUNDLED_LIBS=1 node atlas/samples/native_probes/check-browser.cjs
```

Для необязательного снимка **страницы**, не всего browser chrome, добавь `NATIVE_PROBES_SCREENSHOT=1`. PNG сохранится в исключённой `.local/find-probe/drag-page.png`. Бинарники и node_modules также остаются в `.local`, не в Git. Установка не нужна читателю README и не является запуском AWS.
