# Два листа — один кораблик

18 ноября 2026. Новый экспонат — **два прозрачных изображения, которые раскрывают силуэт при простом совмещении**. Не QR-код, не стереозрение, не исполняемые пиксели: обычное наложение непрозрачных чёрных точек, которое можно повторить на прозрачной плёнке.

Свой рисунок — бумажный кораблик из геометрических парусов и корпуса. Исходная бинарная картинка 128 × 96, каждая доля 256 × 192. На превью листы показаны на белом фоне, чтобы оставаться видимыми в тёмной теме GitHub. Настоящие файлы A и B — RGBA, чёрная краска с альфа 0/255. На чёрной подложке такая краска не видна: используй белую.

## Сначала важное: это не хранилище секретов

**Оба листа, исходник и seed доступны публично. Выбор узоров детерминирован для воспроизводимости. Никакой конфиденциальности эта демонстрация не обеспечивает.** Нельзя подставлять сюда реальные секретные документы и полагаться на слово «криптография».

Более того: по опубликованному seed можно заново получить A и раскрыть **один B без скачивания опубликованного A**. Это проверяется тестом, а не спрятано в примечании. У генератора намеренно нет параметра загрузки пользовательского секретного изображения — он выпускает только собственную открытую иллюстрацию.

Теоретическое свойство классической схемы относится к **свежему независимому равномерному выбору** узора для каждого пикселя и безопасному хранению/передаче долей. Оно не переносится автоматически на повторно используемый seed, публичную случайность, повторное использование доли, метаданные, размеры, неаккуратную печать или целое приложение. Здесь не реализована и не аудирована система защищённого обмена.

## Шесть вариантов одного блока

Для одного исходного пикселя используются четыре позиции:

```text
0 1
2 3
```

Выбираются любые две чёрные позиции из четырёх: всего `C(4,2) = 6` масок. На лист A записывается выбранная маска `P`.

- Белый исходный пиксель: лист B получает **тот же** `P`.
- Чёрный исходный пиксель: лист B получает **дополнение** `¬P`.

В каждом отдельном листе в каждом блоке ровно **2/4 чёрного**. При обычном наложении чёрная точка закрывает прозрачную:

```text
белый оригинал:   P OR P  → 2/4 чёрного
чёрный оригинал:  P OR ¬P → 4/4 чёрного
```

`OR` здесь относится к биту «есть чёрная краска». Если кодировать чёрное нулём, формула в массивах будет `AND`: это смена соглашения, не другой оптический эффект. **XOR при показе не используется.** Средняя непрозрачность всего слоя тоже не уменьшается: отдельный чёрный субпиксель непрозрачен полностью.

### Что именно можно доказать без статистики

Если выбор `P` идеален и равномерен, для любого из двух значений исходного пикселя наблюдатель одного листа видит каждую из шести допустимых масок с вероятностью `1/6`. Для B это верно потому, что дополнение переставляет шесть масок взаимно однозначно. Тест перебирает все варианты и проверяет равенство условных распределений, а не пытается «доказать безопасность» красивой гистограммой.

Одинаковые 50 % чёрного в каждом блоке сами по себе **не доказывают** полную безопасность реализации. В нашем публичном детерминированном примере известный seed разрушает исходную предпосылку. Выбор текстуры сделан через SHA-256 от публичных координат и строки; отбрасывание байтов 252…255 убирает простой перекос `byte % 6`, но **не превращает публичный seed в секретный ключ**.

## Как получен результат, без подрисовки

[Генератор](samples/veil/generate.py) сначала пишет оба RGBA-файла, затем **заново открывает их**, накладывает на белую подложку обычным `Image.alpha_composite` и сохраняет [stack.png](../assets/veil/stack.png). Рисунок-цель в этот шаг не передаётся. На постере результат увеличен только для просмотра; для цифрового наложения используй оригинальные доли, не скриншот.

Отдельная функция `recover_file` читает **только непрозрачный чёрно-белый stack.png**. Считает чёрные точки в каждом блоке 2 × 2 и восстанавливает чёрный исходный пиксель там, где их четыре. Ни seed, ни файлы долей, ни рисунок-цель декодеру не нужны.

Результат этого выпуска:

- 12 288 исходных пикселей.
- По 24 576 непрозрачных чёрных субпикселей в каждой доле.
- **0 ошибок восстановления** из опубликованного наложения.
- Полное соответствие восстановленного PNG и исходника побайтно.

Это проверка конкретных файлов и математической схемы, не «100 % криптографической стойкости» и не результат физической печати. Исходник и восстановление — отдельные файлы, хотя содержимое совпадает: [source.png](../assets/veil/source.png) / [recovered.png](../assets/veil/recovered.png).

## Печатный опыт

[PDF](../assets/veil/sheets-a4.pdf) содержит **два листа A4**, по одной доле на странице:

1. Печатай **100 %**, отключив «подогнать к странице». Измерь контрольный отрезок — 50 мм.
2. Используй только прозрачную плёнку, которую допускает твой принтер. Не клади неподходящую плёнку в лазерный принтер; следуй инструкции производителя.
3. Поле каждой доли — **128 × 96 мм**, отдельный субпиксель — **0,5 × 0,5 мм**. Размеры обеих страниц должны совпадать. Не зеркаль один лист отдельно.
4. Совмести четыре креста и смотри на белой подложке. На непрозрачной бумаге первый лист закроет второй, а не раскроет кораблик.
5. Малый сдвиг, перекос, усадка плёнки, растрирование принтера и просвечивание чёрного могут снизить контраст.

Векторные прямоугольники PDF построены из тех же битовых долей, что PNG. Их положение можно проверить растеризацией PDF, но **реальная печать и совмещение плёнки здесь не испытывались**. Нулевые ошибки цифрового декодера не обещают такой же результат камеры или физической вещи.

## Локальный стол

Распакуй [bench.zip](../assets/veil/bench.zip) и открой `bench.html`. Три файла должны оставаться рядом. Режимы: A, B, A+B. Ползунок сдвигает второй лист, кнопка совмещает точно. Поддержан только целочисленный горизонтальный сдвиг ±12 субпикселей; растяжение, поворот, перспективу и физическую плёнку интерфейс не моделирует.

На canvas рисуются только два экспортированных PNG с обычной композицией. Исходник кораблика не входит в ZIP и в HTML не зашит. Нет сети, аналитики, автопроигрывания, ввода секретов и сохранения прогресса. В README работает обычная ссылка раскрытия; JavaScript запускается лишь в отдельно открытом локальном комплекте.

## Повторение

```sh
python3 -m venv .venv
.venv/bin/pip install -r atlas/samples/veil/requirements.txt
.venv/bin/python atlas/samples/veil/generate.py
# Декодер получает только файл обычного наложения:
.venv/bin/python atlas/samples/veil/generate.py \
  --decode assets/veil/stack.png --output /tmp/recovered-boat.png
# Отдельная перепечатка комплекта:
.venv/bin/python atlas/samples/veil/generate.py --output /tmp/two-sheets
```

Python, Pillow, NumPy, ReportLab; сетевых запросов при генерации нет. Генератор не меняет корневой README. PDF и ZIP имеют фиксированные метаданные для побайтной воспроизводимости. Декодер намеренно требует точный RGB PNG с чёрными/белыми пикселями и чётными размерами: JPEG, сглаженные скриншоты и произвольные сдвиги не поддерживаются и не выдаются за корректный вход.

**Идея для README:** предложить не ещё один баннер, а маленький физический опыт с раскрытием — при обязательной доступной текстовой версии и честной границе между демонстрацией механизма и защищённой системой.
