# Кабинет данных: репозиторий становится иллюстрацией

Продолжение исследования, 18 ноября 2026. После декоративных и математических рисунков — шесть визуализаций настоящих файлов. Не подключаем API статистики, не собираем события посетителей и не используем вымышленные числа.

## Область измерения — важнее красивого графика

Это **явная выборка из 12 файлов, по одному на формат**, а не анализ всего Git-репозитория, всей папки assets или трафика страницы. Список зафиксирован в `SAMPLE` генератора. Выбраны разные материалы галереи: SVG, PNG, GIF, STL, GeoJSON, TopoJSON, TTF, WAV, PDF, notebook, CSV и ZIP. Большой WAV не означает, что README скачивает его при чтении: он открывается отдельно. Архив содержит дубли материалов, поэтому сумма — сумма выбранных файлов, не уникальных данных.

Пути, байты, SHA-256, первые 16 байтов, результат zlib level 9 и гистограммы — в [машиночитаемых измерениях](../assets/cabinet/measurements.json). В [CSV](../assets/cabinet/files.csv) можно искать код файла или расширение штатным просмотрщиком GitHub. Значения измеряются из содержимого файлов, не из даты изменения, размера Git pack, выделенных дисковых блоков или ответа HTTP.

Новый зал сам не входит в выборку: его перепечатка не меняет собственные исходные данные и не создаёт бесконечный цикл изменения размеров. Генератор не читает README, не запускает git и не обращается в сеть. Изменение выбранного файла намеренно требует перепечатать плакаты.

## Что изучено в других GitHub

Смотрел README и исходники напрямую через GitHub API. Ссылки закреплены на исследованных коммитах. Код новых плакатов свой; это не перенос чужой реализации или сторонний workflow.

### D3 Hierarchy: прямоугольники вместо декоративных пузырьков

В [treemap/binary.js](https://github.com/d3/d3-hierarchy/blob/41f11f82647566c90150272210c50188dec4071b/src/treemap/binary.js) родительский прямоугольник делится вдоль длинной стороны, а граница выбирается около половины веса. Исходник использует накопленные суммы и бинарный поиск точки разделения.

У нас своя небольшая реализация того же общеизвестного вида раскладки: сортировка файлов по размеру, выбор ближайшей к половине границы простым перебором и рекурсивное деление. **Площадь пропорциональна байтам**, а не радиус, ширина подписи или важность проекта. Тест проверяет площади, границы и отсутствие перекрытий.

### GitHub OCTO Repo Visualizer: данные отдельно, рисунок отдельно

В [process-dir.js](https://github.com/githubocto/repo-visualizer/blob/a999615bdab757559bf94bda1fe6eef232765f85/src/process-dir.js) обход дерева собирает имя, путь, размер и детей; есть исключения путей. В [Tree.tsx](https://github.com/githubocto/repo-visualizer/blob/a999615bdab757559bf94bda1fe6eef232765f85/src/Tree.tsx) видна отдельная визуальная часть с иерархией, pack, шкалами и цветами расширений.

Полезный приём: не смешивать получение данных с рисованием. Здесь `collect()` возвращает записи, `posters()` строит изображения, а JSON позволяет независимо перепроверить всё численно. Для понятной и стабильной демонстрации выбран небольшой явный набор, а не безграничный обход рабочего каталога.

[README Repo Visualizer](https://github.com/githubocto/repo-visualizer/blob/a999615bdab757559bf94bda1fe6eef232765f85/README.md) прямо называет проект экспериментом. В [action.yml](https://github.com/githubocto/repo-visualizer/blob/a999615bdab757559bf94bda1fe6eef232765f85/action.yml) по умолчанию разрешена отправка коммита, а runtime указан как node16. Это исторический пример архитектуры, **не рекомендация копировать workflow как есть**. В нашем обновлении Actions, токены и автоматический push не добавляются.

### Dust: подпись масштаба важнее эффекта

В [README Dust](https://github.com/bootandy/dust/blob/079c55266917387e416e0f871c97c06da52df12d/README.md) объясняется, как относительные полосы показывают долю подкаталога и связь с родительским размером. Изучен README, не полный исходник программы.

Практический вывод — каждый график должен объяснять, что считается за целое. В кольце это сумма байтов выборки; в диаграмме Парето — две разные подписанные шкалы; в спектрах — доля байтов конкретного файла. Подписей «весь GitHub» или «вес загрузки» нет.

## Шесть готовых способов оформить данные

### 1. Treemap

Каждый файл занимает площадь, пропорциональную его размеру. Цвет и код связывают плитку со списком справа. Мелкие файлы закономерно превращаются в очень узкие области; подпись не пытается втиснуться в них. Граница толщиной один пиксель служит разделителем, математическая пропорция проверяется до отрисовки обводки.

**Когда брать:** объяснить состав релиза или распределение материалов проекта. Для точных чисел оставляй таблицу, не заставляй читателя мерить пиксели.

### 2. Кольцевой атлас

Каждый сектор равен доле байтов выбранного формата, причём здесь действительно по одному файлу на формат. В легенде есть проценты и исходные байты. Проценты округлены до двух знаков, поэтому их сумма на печати может слегка отличаться от 100%.

**Когда брать:** компактная структура набора данных. Для сравнения близких величин лучше столбики. Не подписывай такое кольцо как «языки программирования аккаунта».

### 3. Парето

Столбики показывают байты относительно максимального файла, а линия — накопленную долю **всей выборки**. Слева шкала столбиков не пронумерована: назначение — увидеть ранжирование, точные значения есть в CSV. Правая шкала 0–100% относится только к линии.

**Когда брать:** найти, какие несколько ресурсов формируют основную часть объёма. Наличие двух шкал требует явной подписи: это не два вида одного измерения.

### 4. Сжимаемость

Для каждого содержимого отдельно запускается `zlib.compress(data, 9)`. Полоса — отношение результата к исходному размеру, 100% соответствует фону полной полосы. На уже сжатых данных результат иногда может быть **больше** исходника из-за служебных байтов. Алгоритм не изменяет оригиналы.

**Это не** реальный сетевой трафик GitHub: zlib — не gzip, не Brotli, не размер HTTP-заголовков и не стратегия кеша браузера. Версия runtime zlib записана в JSON; разные версии библиотеки могут давать отличающиеся результаты. Побайтовая воспроизводимость ожидается при одинаковых исходных файлах и среде zlib.

### 5. Паспорт первых байтов

На каждой строке напечатаны первые 16 байтов в hex. Яркость кодирует старшую hex-цифру; полный байт доступен как текст. PNG, GIF, WAV, ZIP, PDF и TTF имеют узнаваемые начала. Но это не универсальный детектор форматов: у SVG может быть XML-декларация, у JSON — пробелы, у ASCII STL — текст, а CSV вообще не обязан иметь сигнатуру.

**Когда брать:** низкоуровневая документация, демонстрация форматов, визуальный указатель типов. Не путай этот рисунок с криптографическим отпечатком: SHA-256 лежит отдельно в CSV.

### 6. Спектр байтов

Четыре файла (SVG, PNG, TTF и WAV) разделены на 16 корзин по старшей hex-цифре: `00–0F`, `10–1F`, …, `F0–FF`. Высота везде имеет одну шкалу 0–100% байтов соответствующего файла. Сумма корзин каждого файла точно равна размеру файла; отметка «пик» показывает самую частую корзину.

**Когда брать:** необычная, но проверяемая обложка бинарного инструмента. По такому спектру нельзя надёжно определить энтропию, качество сжатия, шифрование или безопасность файла.

## Перенести в свой README

1. Скопируй генератор и замени `SAMPLE` своими путями. При другом числе файлов адаптируй компоновку: текущий дизайн рассчитан на 12 строк.
2. Перепечатай SVG и положи их рядом с README.
3. Оставь краткое описание выборки и ссылку на таблицу.
4. Оберни изображение в `<a>` для перехода на CSV или исходник. Внутренние SVG-ссылки не становятся кнопками в `<img>`; если нужны независимые цели перехода, используй несколько отдельных картинок в HTML-таблице.
5. Обновляй файлы по мере изменения данных, не называй статичный результат живой аналитикой.

```sh
python3 atlas/samples/cabinet/generate.py
python3 atlas/samples/cabinet/generate.py --output /tmp/cabinet
python3 -m unittest discover -s tests -v
```

Только стандартная библиотека Python. Все шесть изображений статичны, без JS, SMIL, внешних шрифтов, сетевых запросов и CSS-фильтров. Они имеют `title`, `desc`, собственную подложку и внешнюю текстовую подпись в README. Системный шрифт и сглаживание могут отличаться между клиентами.
