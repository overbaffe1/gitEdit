# Два устойчивых ответа

Две абстрактные стороны **A** и **B**, по восемь участников. Каждый строго ранжирует **всех** участников другой стороны, от лучшего к худшему. Назначение взаимно-однозначное, у каждого ровно один партнёр. Ничьих, неприемлемых партнёров, квот и отсутствующих предпочтений здесь нет.

**Блокирующая пара** — Aᵢ и Bⱼ, не назначенные друг другу, причём оба предпочли бы друг друга своим текущим партнёрам. Назначение устойчиво, если таких пар нет. Это только устойчивость к отклонению пары, не отсутствие любых возможных коллективных изменений и не гарантия справедливости.

## Один вход, два результата

| Кто делает предложения | Сумма позиций для A | Сумма позиций для B | Блокирующих пар |
|---|---:|---:|---:|
| A | 15 | 34 | 0 |
| B | 35 | 11 | 0 |

Позиция **1 — лучшая**, 8 — худшая. Смена предлагающей стороны меняет семь из восьми пар. Обе конечные раскладки устойчивы. Значит, устойчивость сама по себе **не выбирает единственный ответ**.

Суммы рангов приведены для описания примера, а не как целевая функция алгоритма и не как измерение общественного благополучия: ранги порядковые, а разница между соседними местами ничего не говорит о силе предпочтения.

## Что означает преимущество предлагающего

Использован алгоритм отложенного принятия Гейла—Шепли:

1. Свободный участник предлагает следующему по своему списку, кому ещё не предлагал.
2. Получатель предварительно удерживает лучшее из текущего и нового предложений, остальные отклоняет.
3. Отклонённый участник снова попадает в очередь; процесс продолжается, пока все назначены.

«Предложение принято» здесь означает **предварительно удержано**, а не необратимую фиксацию пары. При полном строгом ранжировании и равных сторонах алгоритм завершается устойчивым назначением. Ни одна пара не получает повторное предложение, поэтому предложений не больше n². Наши журналы содержат 15 и 11 предложений. Реализация специально сохраняет полные снимки для стенда, поэтому весь код с построением рангов/журналированием не выдаётся за оптимизированную O(n²) реализацию по времени и памяти.

Оптимальность предлагающей стороны означает: **каждый её участник** получает лучшего партнёра, которого он может иметь **в каком-либо устойчивом полном назначении** при этих предпочтениях. Не лучший вообще, не оптимальная сумма обеих сторон, не случайный перевес первого по очереди участника. «Кто первый» здесь — **какая сторона делает предложения**, а не перестановка очереди внутри одной стороны. Никаких выводов об отсутствии дискриминации или справедливости реальных систем по этому примеру не делается.

## Полный перебор, а не доверие решателю

Всего 8! = **40 320** полных назначений. Независимый `verify.py` не импортирует решатель, его очередь или журнал. Для каждой перестановки он проверяет определение блокирующей пары непосредственно по опубликованным спискам. В этом примере устойчивых назначений ровно **пять**.

Проверяющий сравнивает полный найденный список с `certificate.json` в фиксированном лексикографическом порядке, проверяет устойчивость обоих концов и для **каждого** устойчивого назначения/участника проверяет, что соответствующий предлагающий конец не хуже по его собственному списку. Поэтому здесь преимущество подтверждено исчерпывающей проверкой конкретного входа, а не только ссылкой на название алгоритма.

Пропущенное устойчивое назначение, неверная перестановка или подмена концов обнаруживаются. Устойчивость одного произвольного назначения проверяется за n² сравнений пар (поиск позиции внутри списка добавляет линейную работу в этой простой реализации). Полный перебор факториален; поддерживается только **1…8** участников на каждой стороне. Это не масштабируемый метод проверки рынка на тысячи участников. JSON — переносимые данные для пересчёта, не криптографическая подпись.

Входные списки должны быть перестановками целых меток 0…n−1. Булевы значения не принимаются за целые; повторы, дырки и стороны разных размеров отвергаются. Ограничение размера не является защитой JSON-парсера от произвольно огромных недоверенных файлов.

В стенде можно выбрать предлагающую сторону, пройти процесс по одному предложению или ползунком, а затем обменять партнёров двух A. Обмен — изменение готового назначения, не шаг Гейла—Шепли. Иногда обмен может дать другое устойчивое назначение: стенд **не объявляет любой обмен ошибкой**, а заново проверяет все 64 сочетания. Красная клетка показывает блокирующую пару и рядом объясняется, кого оба участника предпочитают вместо своих текущих партнёров. По умолчанию обмен A1 и A2 в A-предлагающем конце создаёт шесть таких пар.

Для частичного состояния итоговая устойчивость не объявляется и ручной обмен выключен. Полные входные предпочтения всегда видны. Отдельная кнопка запускает в браузере собственный перебор всех 40 320 назначений, сверяет пять устойчивых раскладок и проверяет оба преимущества. GitHub README не исполняет этот JavaScript: он показывает GIF и ссылку на автономный пакет. В самом HTML нет автоматического воспроизведения.

Индексы в JSON — с **нуля**, подписи на рисунках и в CSV — с **единицы**. Любое назначение кодируется массивом `assignment[a] = b`, даже когда предложения делает B. В событиях proposer/receiver относятся к ролям выбранного запуска.

## Воспроизведение

```sh
# Только стандартная библиотека; также работает из распакованного ZIP:
python3 -S atlas/samples/matching/verify.py assets/matching/problem.json assets/matching/certificate.json
# Отрисовка и тесты:
python3 -m venv .venv
.venv/bin/pip install -r atlas/samples/matching/requirements.txt
.venv/bin/python atlas/samples/matching/generate.py
.venv/bin/python -m unittest discover -s tests -p test_matching.py -v
```

Pillow 13.0.0 нужен только для GIF/PNG; картинки и код собственные. Генерация читает сохранённый вход `atlas/samples/matching/problem.json`, а не ищет новый случайный пример. Происхождение входа: `random.Random(119)`, сначала восемь строк A, затем восемь B, каждая `sample(range(8),8)`. Пример выбран из семян 0…118 и 119 по условию не менее семи изменённых пар и не менее пяти устойчивых назначений. Это **подобранный демонстрационный случай**, не оценка типичного распределения результатов.

ZIP имеет фиксированные даты; тест повторной генерации сравнивает все артефакты побайтно в одном окружении. Восемь тестов охватывают полный опубликованный перебор, 24 детерминированных случайных входа размеров 1…6, независимое воспроизведение каждого события, ручной контрпример, порчу/подмену концов, строгие входы, автономный ZIP без site-packages и повторную генерацию. Опциональный `check-browser.cjs` проверяет распакованный ZIP: оба журнала полностью, все пять устойчивых назначений из перебора 40 320, оба преимущества, ручной обмен/шесть блокеров/объяснение, таблицу из 64 клеток, частичные состояния, ползунок, клавиатуру, canvas, мобильную ширину и отсутствие HTTP/JS-ошибок. npm-зависимости указаны в начале скрипта; минимальному Linux нужны библиотеки Chromium.
