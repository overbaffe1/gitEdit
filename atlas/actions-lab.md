# GitHub Actions как ручной пульт эксперимента

[← README](../README.md) · [Открыть workflow на GitHub](https://github.com/overbaffe1/gitEdit/actions/workflows/native-lab.yml)

Здесь демонстрируются три связанные возможности платформы: **типизированная форма запуска**, **Markdown Job Summary** и **скачиваемый artifact**. Это не очередной плакат и не сторонний сервис. Сам опыт работает на странице Actions, а не внутри README.

## Статус: подготовлен, но не запущен в облаке

**Workflow в этой работе не dispatch-ился.** Проверены локальный генератор, YAML и прохождение ссылок через Markdown API. Нет фиктивного успешного run, badge, придуманного artifact URL или заявления об облачной проверке.

Открытие страницы workflow ничего не запускает само по себе. Ручной запуск требует входа, прав записи и разрешённых Actions; определение workflow должно находиться в default branch. Политика репозитория может запретить Actions, выбранные сторонние actions или hosted runners — настройки не включались и не менялись за пользователя.

## Что можно сделать в нативной форме

1. Открыть workflow по ссылке выше.
2. Если доступно, раскрыть **Run workflow**, оставить нужную ветку и посмотреть параметры.
3. `motif`: одиночный выбор `orbit` или `spiral`.
4. `count`: число точек; принимаются только **целые 12–96**, дроби отклоняются скриптом.
5. `palette`: выбор `night` или `paper`.
6. `include_csv`: boolean-флажок, добавляющий координаты в результат.

**Чтобы только посмотреть форму, вторую кнопку Run workflow нажимать не нужно.** Она действительно ставит job в очередь и запускает облачные вычисления. Не обещаем, что это бесплатно для любого аккаунта, репозитория и тарифа. Действуют политика Actions, квоты и условия оплаты. Пять минут timeout — ограничение длительности одной job, **не общий лимит расходов** и не защита от многократных ручных запусков.

## Что произойдёт после осознанного запуска

Runner `ubuntu-24.04` получает исходники, запускает стандартный Python-скрипт и загружает результат как artifact. Нет установки Python-библиотек, генерации коммитов, изменения README, деплоя, Issue или PR. Два actions зафиксированы полными SHA:

- `actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683`;
- `actions/upload-artifact@ea165f8d65b6e75b540449e92b4886f43607fa02`.

Существование этих коммитов проверено GitHub API. Это фиксация зависимостей, **не полный аудит их кода** и не вечная гарантия совместимости с будущими runner-версиями/политиками GitHub.

### 1. Job Summary вместо поиска по логам

Payload дописывает Markdown в файл `GITHUB_STEP_SUMMARY`: таблицу выбранных параметров, число точек, SHA-256 файлов и инструкцию получения результата. GitHub документирует показ такого отчёта на summary-странице запуска после завершения job.

Последний шаг получает **настоящий `artifact-url` из outputs upload-action** и добавляет ссылку в свой summary. URL не угадывается по номеру запуска. Итог зависит от успешного выполнения предыдущих шагов: если генерация/загрузка завершились ошибкой, успешный результат не обещается.

SVG не вставляется относительной ссылкой на файл runner в Summary: такая картинка не становится публичной сама по себе. Смотреть её нужно в скачанном artifact. Содержимое summary также может быть доступно читателям запуска — секреты туда вводить нельзя.

### 2. Artifact как готовый результат опыта

Скачиваемый `native-lab-result` содержит:

- `drawing.svg` — детерминированный рисунок точек по выбранным параметрам;
- `result.json` — параметры, границы координат и SHA-256;
- `summary.md` — текст отчёта;
- `coordinates.csv` — только при включённом флажке CSV.

Upload-action упаковывает файлы в artifact, который скачивается через GitHub. Для загрузки по документации нужен вход и доступ на чтение репозитория. Запрошенный срок хранения — **3 дня**; политика организации/репозитория и возможность загрузки могут влиять на результат. Это не постоянный download URL, не release и не долговечное файловое хранилище.

### 3. Локальный пример без притворства

В репозитории есть [пример отчёта](../assets/actions-lab/example/summary.md), [SVG](../assets/actions-lab/example/drawing.svg), [CSV](../assets/actions-lab/example/coordinates.csv) и [JSON](../assets/actions-lab/example/result.json) для `orbit / 24 / night / true`. Они **сгенерированы локально**, не скачаны из успешного run. И сам отчёт, и JSON это явно обозначают.

Картинка здесь — только полезная нагрузка, чтобы было что получить из реального пульта. Новая возможность GitHub — не расположение кружков, а связь inputs → job → summary → artifact.

## Ограничения и безопасность

- В YAML только `workflow_dispatch`. **Нет push, pull_request, pull_request_target, schedule, workflow_run или repository_dispatch.** Слияние PR не запускает опыт.
- `permissions: contents: read`; checkout не сохраняет credentials. Никаких write-permissions и явно заданных secrets в workflow нет. При работе Actions всё равно использует служебные токены для checkout/artifact — не утверждаем, что платформа обходится вообще без токенов.
- Непроверенные inputs передаются в **env**, а не подставляются в shell-команду. Python проверяет фиксированные значения, целочисленный диапазон и `true/false` до записи файлов.
- Нет eval/exec, shell-вызовов из Python, произвольных URL, пользовательского текста в отчёте или путей из inputs. Поле выбора ветки принадлежит GitHub; перед запуском нужно доверять коду на выбранной ветке.
- Output расположен в runner.temp. Непустой output-каталог отклоняется, чтобы не загрузить смесь старых и новых файлов; чужие файлы автоматически не удаляются.
- Payload не делает сетевых запросов; checkout и upload, разумеется, работают с сетью. Это не offline-процесс целиком.
- При закрытии страницы уже запущенная job не исчезает. Остановить её нужно средствами Actions при наличии прав.

## Проверка локально

```sh
LAB_MOTIF=spiral LAB_COUNT=36 LAB_PALETTE=paper LAB_INCLUDE_CSV=false \
LAB_OUTPUT=/tmp/native-lab-my-result \
python atlas/samples/actions_lab/run.py
```

Выбери новый или пустой output-каталог. Вне Actions переменную `GITHUB_STEP_SUMMARY` задавать не нужно: отчёт окажется в `summary.md` рядом с результатом. Если задать её как путь к файлу, скрипт допишет туда отчёт — это имитация интерфейса environment file, **не загрузка в GitHub**.

Для воспроизведения примера и вставляемого блока:

```sh
python atlas/samples/actions_lab/generate.py
python -m unittest discover -s tests -p test_actions_lab.py -v
```

Генератор не меняет README/workflow, не создаёт коммиты и не выполняет dispatch. [Workflow](../.github/workflows/native-lab.yml) · [Payload](samples/actions_lab/run.py) · [Генератор примера](samples/actions_lab/generate.py) · [SHA-256](../assets/actions-lab/manifest.json).

Тесты покрывают входы, отклонение недопустимых значений, детерминизм комбинаций, соответствие SVG/CSV/JSON, optional CSV, дописывание summary, защиту от смешивания файлов, разрешения и отсутствие автотриггеров. Это собственная проверка выбранного поднабора YAML, не замена GitHub validator и не доказательство успешного облачного run. Предыдущее содержимое README сохраняется побайтово.

## Исследование

Изучены относящиеся к стенду разделы **пяти официальных документов github/docs**: manual workflow run; workflow syntax (inputs, permissions, timeout); workflow commands (job summary); artifacts; downloading artifacts. [Закреплённые SHA, пути и постоянные ссылки](samples/actions_lab/sources.json).

Авторизованная форма Run workflow, очередь runner, реальная загрузка artifact и облачный Summary **не проверялись**: облачный запуск сознательно оставлен пользователю, с предупреждением о ресурсах. Политики репозитория и настройки оплаты не изменялись.
