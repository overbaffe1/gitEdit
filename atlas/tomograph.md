# Предмет из одних теней

18 ноября 2026. После прямого расчёта гравитационной линзы — **обратная задача**. Можно ли восстановить сечение детали, если известны только интегралы вдоль прямых с разных направлений?

Здесь собственный синтетический объект: круглая деталь с тремя отверстиями и более плотной эллиптической вставкой. Не медицинский снимок, не пациент, не реальный рентген и не стандартный чужой phantom. Измерения рассчитываются аналитически, затем **самостоятельный реконструктор получает только опубликованный CSV**.

## От предмета к измерениям

Объект — сумма пяти эллиптических областей: внешний диск, три отрицательных вклада-отверстия и положительная вставка. Итоговая плотность неотрицательна. Для изображения исходник семплируется на сетке 192 × 192, но проекции **не получены вращением этого растра**: интеграл каждого эллипса вычисляется аналитически. Это убирает скрытую зависимость измерений от выбранной сетки реконструкции, хотя вся задача всё равно идеально синтетическая.

Для плотности `f(x,y)` проекция под углом `θ`:

```text
pθ(s) = ∫ f(x,y) δ(s − x cosθ − y sinθ) dx dy
```

Это линейный интеграл, не сырая интенсивность прошедшего излучения. Настоящий детектор потребовал бы модели измерения, калибровки и, для соответствующей модели поглощения, логарифмического преобразования. Здесь никакое излучение не создаётся.

У эллипса с полуосями `a,b`, поворотом `φ`, центром `(cx,cy)` и плотностью `ρ`:

```text
w = sqrt(a² cos²(θ−φ) + b² sin²(θ−φ))
t = (s − cx cosθ − cy sinθ) / w
pθ(s) = 2ρab/w × sqrt(max(0, 1−t²))
```

Тест отдельно проверяет эту формулу на окружности, а также сохранение полной массы: интеграл каждой проекции по детектору должен совпадать с интегралом плотности по плоскости в пределах дискретизации.

## CSV — единственный вход обратной задачи

[projections.csv](../assets/tomograph/projections.csv) содержит:

- 256 строк детектора `s ∈ [−1,25; +1,25]`;
- первый столбец `detector_s` с координатами;
- 120 столбцов `angle_000.0`, `angle_001.5`, …, `angle_178.5`;
- в каждой ячейке — линейный интеграл, округлённый до восьми знаков.

Размер файла **342 827 байт**. Углы и шаг детектора считываются из самого CSV. Единственная дополнительная договорённость реконструктора — выходное поле `x,y ∈ [−1;1]` и размер 192 × 192. Все величины условные, не измерения реальной детали в мм.

После записи генератор заново открывает **округлённый опубликованный файл**, и реконструкция работает именно с ним, а не с более точным внутренним массивом. Код [reconstruct.py](samples/tomograph/reconstruct.py) вообще не импортирует генератор или описание эллипсов. Для отдельного запуска не нужны source.png, facts.json, proof.png или какой-либо target.

## Почему «сложить тени» недостаточно

Обычная обратная проекция размазывает каждое измерение обратно вдоль соответствующей прямой. Складывание таких полос создаёт размытый объект. Чтобы компенсировать это частотное взвешивание, применяется ramp-фильтр.

В нашей договорённости Fourier transform использует частоты в циклах на единицу `s`:

```text
qθ = inverse_FFT(FFT(pθ) × |frequency|)
f_est(x,y) = Δθ × Σ qθ(x cosθ + y sinθ)
```

Перед FFT проекции дополняются нулями до 512 отсчётов, интерполяция детектора линейная. Для полного равномерного набора `Δθ = π/N`. Множители зависят от определения фильтра: библиотека с фильтром `2|frequency|` закономерно может использовать `π/(2N)` — это не обязательно ошибка вдвое.

Наша версия — простой sampled ramp, без улучшенной дискретной поправки на смещение, окон, регуляризации и подавления шума. Небольшой фон, ringing у границ, недовосстановленные края и отрицательные значения численного результата не прячутся из метрик. Обрезка применяется **только к отображению PNG**.

## Что проверено численно

Относительная ошибка определена как `||reconstruction − source||₂ / ||source||₂` по всем 192 × 192 значениям **до** clipping и масштабирования показа:

| Опыт | Относительная L2-ошибка |
| --- | ---: |
| 120 проекций по диапазону [0°,180°), FBP | 0,10030644 |
| 8 проекций равномерно по всему диапазону, FBP | 0,55342092 |
| 60 проекций только в [0°,90°), FBP с весом доступного диапазона | 0,63632122 |

Это значения для одного собственного phantom, без измерительного шума. Они **не означают** «90 % диагностической точности», универсальное преимущество метода или гарантию для других объектов.

Для плаката без фильтра используется масштаб показа **4,5**, для FBP и source — **1,5**. Это намеренно подписано: панели сравнивают форму/размытие, не абсолютную яркость. Нормировка численных массивов при подсчёте ошибок от этого не меняется.

### Разреженные и недостающие углы — разные проблемы

В анимации сначала берутся 2, 3, 4…120 равномерно расположенных направлений из **всего** диапазона. Это не буквальная временная запись одного прохода сканера: кадры показывают разные плотности угловой выборки. Числа кадров выбраны как делители 120, поэтому выборка в каждом из них равномерна.

На [proof.png](../assets/tomograph/proof.png) есть отдельный опыт: 60 направлений из первых 90°, а не 60 равномерно по всем 180°. Отсутствующий сектор даёт направленные артефакты. Такой набор не становится полноценным просто потому, что число проекций больше восьми.

## Живой реконструктор

[ZIP](../assets/tomograph/bench.zip) содержит один `bench.html`. После распаковки он работает без сервера и сети:

- встроены только массивы координат, углов и округлённых проекций из CSV;
- собственная radix-2 FFT вычисляет ramp-фильтрацию при открытии;
- выбор числа проекций заново выполняет обратную проекцию;
- переключатель сравнивает filtered/unfiltered backprojection;
- кнопка возвращает 120 + фильтр.

В HTML нет исходной картинки, геометрии эллипсов, нейросети, готовых кадров и внешних библиотек. Canvas 128 × 128 выбран для простого CPU-расчёта. Все варианты UI равномерно распределяют выбранные углы по [0°,180°); опыт ограниченного диапазона показан отдельно в proof, не выдаётся за тот же режим.

`bench-reference.png` — Python-эталон **для браузерного теста**, а не вход приложения. Сам ZIP не содержит ни PNG, ни CSV-файла рядом: данные уже внутри HTML. Численный рендер выполняется только при действии пользователя; автопроигрывания, аналитики, сохранения прогресса и загрузки пользовательских данных нет.

GitHub не исполняет этот JS в Markdown. В README видны PNG/GIF и ссылки; для живого опыта нужен отдельно открытый файл. Текстовое объяснение и неподвижный постер доступны без приложения и без анимации.

## Ограничения

Нет реального рентгеновского источника, медицинских изображений, пациента и диагностического применения. Нет cone-beam/fan-beam геометрии, 3D, шума, рассеяния, beam hardening, движения объекта, калибровочных ошибок, PSF, дозиметрии и восстановления по произвольным неравномерным углам. CSV-loader намеренно требует равномерную сетку детектора и углы полного диапазона; не является импортёром файлов настоящих сканеров.

Работа со своими аналитическими данными — не независимая валидация на реальных измерениях. Экспонат показывает, **как устроена и где ломается** простая обратная задача, а не делает научные или медицинские выводы.

## Повторить

```sh
python3 -m venv .venv
.venv/bin/pip install -r atlas/samples/tomograph/requirements.txt
.venv/bin/python atlas/samples/tomograph/generate.py
# Реконструкция только из опубликованного CSV:
.venv/bin/python atlas/samples/tomograph/reconstruct.py \
  assets/tomograph/projections.csv --output /tmp/reconstruction.png
.venv/bin/python atlas/samples/tomograph/reconstruct.py \
  assets/tomograph/projections.csv --views 8 --output /tmp/eight.png
.venv/bin/python atlas/samples/tomograph/reconstruct.py \
  assets/tomograph/projections.csv --plain --output /tmp/plain.png
```

Только NumPy, Pillow и стандартная библиотека. Генератор не делает сетевых запросов и не редактирует README; `--output /tmp/tomograph` создаёт отдельный комплект. ZIP имеет фиксированную дату. Для исторического набора тестов нужны зависимости старых экспонатов.

**Идея для README:** не только показывать красивый результат, но и отдавать данные, из которых его действительно можно восстановить, вместе с наглядными контрпримерами — мало измерений, отсутствующие направления, неправильный фильтр.
