# Координаты без цифр

18 ноября 2026. Можно ли определить своё место на узоре, видя только маленькое окно? Да, если окна подобраны так, что не повторяются. Но **уникальность и исправление ошибок — разные свойства**.

Здесь собственный воспроизводимый бинарный узор из максимальной линейной последовательности: 63 столбца × 65 строк, 4095 позиций на математическом торе. Все ориентированные окна 4×4 уникальны. Для устойчивости берём 6×6: их минимальное попарное расстояние Хэмминга равно 7, значит любые три ошибки исправляются однозначно.

Это цифровая модель с известной сеткой, масштабом, бинарной полярностью и ориентацией, **не работающий camera detector**. Нет перспективного выравнивания, поиска границ клеток, печатного эксперимента, физического трекинга и неизвестных поворотов. Подход основан на известных идеях m-sequences и coding theory, не объявляется новым изобретением.

## Как построен лист

Генератор начинает с 12-битного состояния `1`. На каждом шаге сохраняет младший бит, затем:

```text
feedback = bit0 XOR bit1 XOR bit4 XOR bit6
state_next = (state >> 1) OR (feedback << 11)
```

Эквивалентная рекурсия последовательности:

```text
s[n+12] = s[n] XOR s[n+1] XOR s[n+4] XOR s[n+6]
```

Полный цикл **4095 = 2¹²−1** проверен перебором состояний: повторов раньше нет, после 4095 шагов возвращается 1. Нулевое состояние в цикл не входит.

Длины сторон 63 и 65 взаимно просты, их произведение 4095. Применяем Chinese remainder mapping:

```text
index(x,y) = (2080x + 2016y) mod 4095
pattern[y][x] = s[index(x,y)]
```

У `index` остаток `x` по модулю 63 и `y` по модулю 65. Поэтому карта проходит все фазы последовательности ровно раз и сохраняет фиксированные фазовые сдвиги при перемещении по каждой оси.

Модель узора **тороидальная**: `x` берётся modulo 63, `y` modulo 65. Окно через край составляется из разных краёв массива. На обычном распечатанном прямоугольнике такой переход **не является** одним непрерывным camera crop; для физической работы потребовалось бы отдельное решение границ/повторения и геометрии.

Это m-sequence-derived array, **не** FFMS de Bruijn construction из просмотренного проекта и не заявление о perfect 12-bit rectangular window. Мы проверяем конкретные 4×4/6×6 окна, а не переносим свойства похожего имени.

Генератор сначала пишет CSV, затем перечитывает **опубликованный файл** для всех проверок и кадров. Декодер не обращается к LFSR construction, истинным координатам или исходному PNG: достаточно карты и наблюдаемого bit patch.

Все координаты zero-based: `x = 0…62`, `y = 0…64`. Это **верхний левый угол** ориентированного окна, не его центр. Bits читаются по строкам сверху вниз, внутри строки слева направо, первый бит — старший. Ноль чёрный, единица белая.

## Уникальность — ещё не коррекция

У всех 4095 окон 4×4 разные signatures. Поэтому чистого 16-битного окна достаточно для локализации в этой модели.

Но минимальная дистанция между такими кодами всего **1**. Существуют две разные позиции, отличающиеся одной клеткой. Ошибка может превратить один допустимый код в другой. Из «все окна разные» не следует «декодер устойчив к шуму».

Берём окно 6×6, то есть 36 bits. Дополнительные клетки не увеличивают количество позиций, но добавляют избыточность. Теперь минимальная дистанция между двумя различными допустимыми окнами **7**.

Это не полный de Bruijn torus размера 6×6: такой содержал бы все `2³⁶` слова. У нас только 4095 допустимых слов из огромного множества. Именно разреженность кодовой книги даёт расстояние между ними.

## Как проверяется расстояние 7

[audit.py](samples/locator/audit.py) получает только CSV:

1. Перебирает **все 4095** положений с wrap и строит signatures.
2. Проверяет, что все 6×6 слова различны и среди них нет нуля.
3. Добавляет нулевое слово и вычисляет Gaussian rank над **GF(2)** посредством XOR.
4. Получает ранг **12** и размер множества **4096 = 2¹²**.

Множество содержится в своём линейном span. Если его размер равен размеру span, оно совпадает со всем пространством. Значит, после добавления нуля это полное 12-мерное линейное code space.

Разность двух слов — XOR — снова ненулевое слово этого пространства. Минимальный ненулевой вес проверяется перебором всех 4095 слов и равен **7**. Для множества всех ненулевых слов минимальное попарное расстояние тоже 7: для минимального слова `w` выбираем `a ≠ 0,w`; оба `a` и `a XOR w` присутствуют и отличаются на `w`.

Это объясняет точный сертификат без миллионов pair comparisons в самом runtime-аудите. **В тестах есть и независимая полная проверка всех 8 382 465 пар**, которая также даёт 7. Таким образом, код не полагается только на пояснение к LFSR или на имя конструкции.

Для 4×4 аналогичный exact rank/cardinality audit даёт minimum distance 1. Утверждения относятся к фиксированному направлению чтения и бинарным flips, не к произвольной image distortion.

## Что гарантирует декодер

Расстояние Хэмминга — число клеток с разными битами. Декодер сравнивает наблюдение со всеми 4095 эталонными окнами и принимает ответ, только если существует **единственный** кандидат на расстоянии не больше 3.

Поскольку `2×3 < 7`, шары радиуса 3 вокруг разных codewords не пересекаются. Если настоящее окно испорчено не более чем в трёх клетках, правильный кандидат обязательно есть и второго быть не может.

Это гарантия для **любой позиции и любой комбинации до трёх flips** при выполнении остальных допущений. В тестах её основания проверены глобально; дополнительно для одной позиции `(9,12)` реально декодированы все:

```text
C(36,0)+C(36,1)+C(36,2)+C(36,3) = 7807
```

вариантов. Не заявляется перебор всех error patterns во всех позициях — это значительно больший набор, ненужный после доказательства disjoint balls.

## Четыре ошибки: не обязательно отказ

У контрольного окна истинная позиция `(9,12)`. Находим другое допустимое окно в `(11,4)` на расстоянии 7. Переворачиваем **четыре** из семи различающихся битов в сторону второго окна. Наблюдение находится:

- в четырёх flips от истинного `(9,12)`;
- в трёх flips от чужого `(11,4)`.

Декодер честно выполняет свой контракт и принимает **(11,4)**. Он не знает, что ошибок было четыре: это знает только симулятор, который внёс порчу.

Поэтому интерфейс отдельно выводит:

- **decoder result** — из bits + map;
- **simulator truth** — исходные X/Y и фактическое число flips;
- явную надпись, если принятый ответ неверен.

Нельзя подавать ground truth в декодер для красивого отказа после четырёх ошибок — так получилось бы скрытое знание ответа. Наш контрпример опубликован как TXT, его можно отдельно передать CLI и получить то же неверное принятие.

Для нулевого 6×6 окна ближайшие допустимые слова имеют вес не меньше 7, поэтому ни одного кандидата в радиусе 3 нет: это отдельный честный **отказ**, не подстановка прежней координаты.

## Живой опыт

[bench.zip](../assets/locator/bench.zip) содержит один `bench.html`. После распаковки открой локально, без сервера/сети:

- Click по карте или X/Y slider выбирает источник окна и сбрасывает flips.
- 36 кнопок-клеток переключают bits; доступны с клавиатуры, имеют подписи строки/столбца и состояния.
- «Три ошибки» вносит три заранее выбранных разных flips относительно чистого окна.
- «Четыре: контрпример» строит неверное принятие через distance-seven partner для текущего окна.
- «Нулевое окно» демонстрирует отказ.
- «Через край тора» выбирает `(61,63)` и явно демонстрирует synthetic wrap.
- «Сбросить ошибки» оставляет позицию, но возвращает чистые bits.
- «Проверить все позиции» пересчитывает uniqueness/rank/weight непосредственно из карты.

Встроена только binary map и собственный код; codebook строится при открытии. Нет lookup готовых результатов по X/Y, PNG/GIF внутри HTML, image matching или передачи truth в `decode`. Вся информация для локализации действительно заключена в 36 битах и известной карте.

36-bit words в JS хранятся как **BigInt**, не в обычных 32-битных bitwise numbers. Это важно: иначе старшие четыре бита терялись бы незаметно. Browser test сверяет все 4095 words с Python, в том числе старшие биты.

Красная рамка означает flip, известный **симулятору**, а не автоматически обнаруженный ошибочный бит. Исправление означает восстановление координаты; приложение не утверждает, что camera pipeline уже нашёл и выделил настоящие дефекты бумаги.

В HTML нет autoplay, `requestAnimationFrame`, внешних библиотек, пользовательской загрузки и сети. В README работает GIF/reduced-motion постер и ссылки; GitHub не исполняет приложение в Markdown.

## Что осталось за пределами

- Известны orientation, scale, grid alignment и black/white polarity. Нет автоматического определения поворота, mirror, перспективы и инверсии контраста.
- Нет subpixel localization, lens distortion, homography, blur/illumination compensation, пропущенных/лишних строк клеток и occlusion erasures.
- Noise model — произвольно расположенные **binary bit flips**, без вероятностной модели и предположения о независимости; не общая optical noise model.
- Нет кодирования датчика, цифровой подписи, секретности и QR compatibility. Это не универсальная замена AprilTag/ArUco и не подготовленная система структурированного света.
- Лист можно открыть/скачать, но физическая печать и camera-read не проверялись. Слово «лист» здесь образ, не отчёт об испытании бумажного носителя.

## Повторить без генератора

Для декодера и аудитора — только standard library Python:

```sh
python3 atlas/samples/locator/locate.py \
  assets/locator/pattern.csv assets/locator/three-flips.txt
# -> accepted, X=9, Y=12, distance=3

python3 atlas/samples/locator/locate.py \
  assets/locator/pattern.csv assets/locator/four-flips-wrong.txt
# -> accepted, X=11, Y=4, distance=3 (неверный ответ вне гарантии)

python3 atlas/samples/locator/locate.py \
  assets/locator/pattern.csv assets/locator/zero-rejected.txt
# -> rejected, exit code 2

python3 atlas/samples/locator/audit.py assets/locator/pattern.csv
```

Для отдельной папки нужны `codebook.py` + `locate.py` (или `audit.py`), CSV и TXT. Ни исходный генератор, ни LFSR seed, ни GIF, ни certificate JSON, ни Pillow/NumPy не требуются.

Генератору нужен только Pillow:

```sh
python3 -m venv .venv
.venv/bin/pip install -r atlas/samples/locator/requirements.txt
.venv/bin/python atlas/samples/locator/generate.py --output /tmp/locator
```

Он не делает сетевых запросов и не меняет README. ZIP имеет фиксированную дату; все артефакты воспроизводятся побайтово в закреплённом окружении. CSV/patch parser намеренно принимает только свой размер карты и ориентированное 6×6 окно, не произвольные изображения.
